# Forklift, AngKorGit и GitComet: сравнительный анализ (2026-10-26)

Сравнение с двумя open source клиентами, ближайшими к нам по задаче («открытый GitKraken»):

- **AngKorGit** — https://github.com/cheat2001/angkorgit (main @ `14a3ed8`, 2026-10-22, релиз v0.24.0), MIT;
- **GitComet** — https://github.com/Auto-Explore/GitComet (dev @ `22525e6`, 2026-10-26, релиз v0.3.2), AGPL-3.0-only;
- **Forklift** — этот репозиторий (main @ `a3acb88`).

Источники: исходники обоих проектов (клоны), их README и docs, GitHub API (звёзды, issues, релизы) и
собственные замеры (раздел 3). Помечено **[предположение]** то, что не подтверждено кодом, документацией или
замером. Код GitComet (AGPL) не копировался и не переносился — только идеи и ссылки.

## Коротко

- **GitComet** — самый быстрый и самый «тяжёлый» по инженерии проект (≈ 930 тыс. строк Rust, 25 крейтов):
  индекс истории на миллионы коммитов, рендеринг на GPU (GPUI от Zed), встроенный difftool/mergetool с
  совместимостью KDiff3/Meld, LFS и git-annex, широкая дистрибуция (apt, AUR, Homebrew, Microsoft Store, RPM).
  Слабые места: нет интеграций с хостингами и AI в открытой версии (обещаны в платной Professional), нет
  drag-to-merge и undo операций, нет настройки хоткеев и i18n, AGPL.
- **AngKorGit** — ближе всех к GitKraken по UX и шире всех по «повседневным» фичам: PR в GitHub/GitLab/
  Bitbucket, AI (API и локальные CLI-агенты), undo, drag-to-merge, группы репозиториев, автообновление с
  проверкой подписи. Слабые места: всё на libgit2 (хуки не запускаются, sparse checkout не учитывается),
  постраничная история с полной сортировкой на каждую страницу, один основной автор (≈ 94 % коммитов).
- **Forklift** по фичам на уровне AngKorGit (а в части хостингов — шире: Forgejo, GitVerse, GitHub, GitLab, PR **и**
  issues), git CLI для операций (хуки, подпись, LFS работают как в терминале), настраиваемые хоткеи, но
  проигрывает обоим в **памяти и в больших репозиториях**: на истории linux (1,5 млн коммитов) первая страница
  графа появляется через 10–20 с, главный процесс растёт до 5 ГБ и падает (раздел 3). Нет AI, bitbucket,
  автообновления и подписанных сборок; проект самый молодой (с 2026-10-22).

## 1. Архитектура

| | Forklift | AngKorGit | GitComet |
|---|---|---|---|
| UI | Electron 45 (Chromium) + React 19, Monaco для diff/конфликтов | Tauri v2 (системный WebView: WebKitGTK / WKWebView / WebView2) + React, Zustand | Rust + GPUI (UI-тулкит Zed), рисует на GPU (Vulkan/Metal/DX, EGL — запасной) |
| Backend | Node в main: nodegit (форк libgit2) для чтения, `git` CLI для всех операций | Rust: git2 (libgit2, vendored) почти для всего; `git` CLI — для сети и `stash apply/pop` | Rust: gix (gitoxide) для чтения, `git` CLI для записи (`commit`, rebase, LFS…) |
| Объём кода | ≈ 28 тыс. строк TS | ≈ 39 тыс. строк TS + 15 тыс. Rust | ≈ 930 тыс. строк Rust в 25 крейтах (вкл. тесты) |
| Хуки, подпись, LFS как в терминале | да (всё пишет `git`) | хуки — **нет** (коммит через libgit2; открытый issue #82), подпись — своя реализация через `ssh-keygen`/`gpg` (`core/sign.rs`) | да (коммит — `git commit`, `porcelain.rs` → `commit_identity_impl`) |

**Граф коммитов.**

- *Forklift* — `src/main/history/service.ts`: revwalk nodegit по всем ссылкам в порядке `--date-order`, кусками по
  2000, раскладка дорожек `GraphLayout` (инкрементальная) в main; окно получает строки страницами
  (`history:rows`, до 1000), список виртуализирован. Кэш — все пройденные строки в памяти main. Лимита на длину
  истории нет. Сортировка libgit2 требует подготовки всего обхода до первой строки (на linux — 10–20 с, раздел 3).
- *AngKorGit* — `apps/desktop/src-tauri/src/core/history.rs`: на **каждую** страницу (200 коммитов,
  `features/graph/store.ts`) открывается новый revwalk с `TOPOLOGICAL | TIME` и пропускаются `skip` первых
  коммитов: каждая подгрузка стоит полной сортировки, глубокая прокрутка — квадратична **[оценка по коду]**.
  Раскладка — `packages/core/src/graph/layout.ts` (инкрементальная, в окне), виртуализация —
  `@tanstack/react-virtual`. Заявлено «100 тыс. коммитов как пятьдесят»; на миллионах — не заявлено.
- *GitComet* — индексированная история (`crates/gitcomet-core/src/history_index.rs`,
  `crates/gitcomet-git-gix/src/repo/log/{index,cache}.rs`, `crates/gitcomet-ui-gpui/src/view/history_graph.rs`):
  компактный индекс топологии (+ commit-graph), контрольные точки раскладки каждые 1024 строки, окна по 256
  строк читаются за миллисекунды. По их замерам (`docs/indexed-history-performance.md`): chromium
  (1,92 млн коммитов) — индекс за ≈ 5,3 с, 63 МиБ; 2 млн строк и 5261 дорожка — построение 1,41 с, отрисовка
  кадра p95 4,4 мс в release. Отдельный режим «только от HEAD» по умолчанию («Full reachable» в заголовке).

**Многопоточность, кэш, обновление с диска.**

- *Forklift*: main — один поток JS, тяжёлое (git CLI, терминал, nsfw-наблюдатель) в отдельных процессах
  (utilityProcess / process host) и в потоках libuv; операции записи сериализуются `RepoQueue` на репозиторий;
  состояние — Redux в main, реплицируется в окно; слежение — nsfw, отсеивание шума `.git`.
- *AngKorGit*: каждая команда — `spawn_blocking` в Tokio; слежение — `notify` с дебаунсом 400 мс, фильтр `.git`
  до HEAD/refs/index (`src-tauri/src/watcher.rs`); кэш — только страницы в Zustand.
- *GitComet*: акторная схема `AppStore` (сообщения → редьюсер → эффекты на пулах исполнителей,
  `crates/gitcomet-state`), отмена (`CancellationToken`) на всех чтениях, коалесценция однотипных загрузок,
  эпохи для отбрасывания устаревших ответов; слежение — свой крейт `gitcomet-fs-watch` (FSEvents на macOS с
  ограничением ресурсов); кэши истории/дорожек/декораций независимы.

## 3. Производительность

### Как мерили

Машина владельца: Linux x86_64, 30 ГБ ОЗУ, приложения — в Xvfb 1600×1000 с программным рендерингом, каждый запуск
с чистым HOME, по 2 повтора. Репозитории:

- **git/git** — 85 803 коммита, ≈ 4,5 тыс. файлов;
- **linux** — 1 501 548 коммитов, клон `--filter=blob:none --sparse` (вся история, рабочее дерево — 18 файлов,
  97 217 записей индекса помечены skip-worktree); для чистого замера истории Forklift — его копия `linux-hist`
  с пустой веткой (тот же граф, status пустой);
- **wide** — синтетика: 200 001 файл, 100 изменённых, 50 новых, файлы 8 МБ и 24 МБ с изменениями каждые 997 строк.
  `git status` на нём — 0,13 с.

Метрики «запуска» одинаковые для всех (`launch_bench.py`): время до видимого окна; время, пока дерево процессов
не затихнет (< 3 % CPU 2 с подряд) — **косвенный** признак «репозиторий загружен», не время до первого кадра
графа; CPU-секунды до этого момента; PSS всего дерева процессов. Forklift дополнительно измерен изнутри через
DevTools (точные времена). Скриншоты каждого запуска проверены глазами.

**AngKorGit замерить не удалось**: AppImage v0.24.0 под Xvfb не рисует окно («Could not create default EGL
display: EGL_BAD_PARAMETER. Aborting», плюс конфликт встроенных библиотек с системным gvfs), и **на рабочем
столе владельца тоже висит пустое окно**. Его цифры ниже — оценки по коду.

### Выводы по производительности

1. **Большая история — наше слабое место.** На 1,5 млн коммитов мы в 3–4 раза медленнее GitComet до рабочего
   состояния и в 3–5 раз тяжелее по памяти, а при прокрутке в конец — падаем. Причины (по коду и профилю памяти):
   сортированный revwalk libgit2 готовит весь обход до первой строки; каждая строка истории в main — объект JS с
   sha, текстами, авторами и рёбрами графа (порядка нескольких КБ на строку **[оценка по росту памяти]**); вся пройденная история держится в памяти.
2. **Отладочные проверки Redux включены в production.** `@reduxjs/toolkit` в main не бандлится и выбирает сборку
   по `NODE_ENV`, а в упакованном приложении он не задан — работают `serializableCheck`/`immutableCheck`,
   которые на каждый dispatch обходят всё состояние (в логе: «SerializableStateInvariantMiddleware took 104ms»).
   Лёгкое исправление, выигрыш на больших репозиториях — **[ожидаемо заметный, не измерен]**.
3. **Sparse checkout ломает status** у нас (и, по коду, у AngKorGit): libgit2 не понимает skip-worktree. Плюс
   список изменений не рассчитан на ~100 тыс. записей (окно до 5,5 ГиБ).
4. Обычные репозитории (git/git, 200 тыс. файлов) — мы на уровне GitComet по времени, но тяжелее по памяти
   (Electron: 8 процессов).

**Лицензии и что можно заимствовать.**

- *AngKorGit — MIT.* Код можно переносить при сохранении копирайта и текста лицензии (NOTICE/файл лицензий).
  Удобно для небольших чистых модулей (например, парсер конфликтов или word diff), но у нас другой стек
  (TS в main/renderer против Rust): переносить придётся идеи и алгоритмы, а не файлы.
- *GitComet — AGPL-3.0-only (+ CLA для контрибьюторов, «двойная» модель).* Любой перенос кода (и переводы на
  TS/производные работы) делает наш продукт производным → он тоже должен распространяться под AGPL с исходниками
  для всех пользователей, включая сетевых. Для нас это значит: **не копировать и не «переписывать близко к
  тексту»** их код; можно — идеи, опубликованные описания (их docs), общеизвестные алгоритмы и формат
  `git difftool/mergetool`-вызовов (это интерфейс git, а не их код). Бенчмарки и цифры из их docs — можно
  цитировать со ссылкой. **[не юридическая консультация; если будем закрывать код или продавать — сверить с
  юристом]**.

## 6. Сильные стороны конкурентов, которых нет у нас, и наши преимущества

### AngKorGit

Есть у них, нет у нас:

1. **AI**: сообщение коммита, ревью staged-изменений, объяснение коммита и конфликта, описание PR — через API
   (OpenAI, Anthropic, Gemini, Ollama, LM Studio) или через уже установленные CLI-агенты пользователя (Claude Code,
   Copilot CLI, Codex, Gemini CLI…) без ключей (`packages/core/src/ai/*`, `src-tauri/src/ai_cli.rs`).
2. **Автообновление с проверкой подписи** и подписанные бесплатно Windows-сборки (SignPath Foundation).
3. **Группы репозиториев**: fetch/pull для группы с итогом по каждому (`src-tauri/src/core/group_update.rs`).
4. **Bitbucket Cloud** и PR из форка в upstream; image diff; stash отдельных файлов; черновики сообщения
   коммита на репозиторий (`features/commit/draftStore.ts`).
5. **Демо-бэкенд в браузере** (`apps/desktop/src/core/demo.ts`): UI разрабатывается и проходит e2e без нативной
   сборки.

Наши преимущества:

1. Все операции через `git` CLI: **хуки работают** (у них — нет, issue #82), LFS и подпись — как в терминале.
2. **Issues**, а не только PR; Forgejo/Gitea и GitVerse; checkout PR из форка; markdown в обсуждениях.
3. **LFS, gitflow, полноценные подмодули**, настраиваемые хоткеи, свои темы файлами.
4. Своя модель безопасности: sandbox, CSP, fuses, проверка IPC; токены привязаны к серверу.
5. Работает на этой машине (их AppImage — нет).

### GitComet

Есть у них, нет у нас:

1. **Индексированная история** на миллионы коммитов (≈ 1,4 с на 2 млн строк, ≈ 60 МиБ для chromium) и
   GPU-рендеринг графа.
2. **Встроенный difftool/mergetool** (`gitcomet setup`, совместимость с аргументами KDiff3/Meld, headless-режим).
3. **3-way merge с autosolve**, Difftastic (структурный diff), image/markdown/диаграммы в превью, огромные файлы.
4. **LFS-блокировки и git-annex**, проверка подписей коммитов, sparse checkout.
5. **Дистрибуция**: apt-репозиторий, AUR, GURU, Homebrew, Microsoft Store, RPM, x64 и arm64; crash-отчёты с
   предзаполненным issue; бюджеты производительности в CI.

Наши преимущества:

1. **Интеграции с хостингами** (PR, issues, 4 провайдера) — у них только в будущей платной версии.
2. **Undo операций и drag-to-merge/rebase**, настраиваемые хоткеи.
3. **Gitflow**, профили и SSH/GPG-ключи с генерацией, встроенный терминал с профилями.
4. Лицензия свободна в выборе (у них AGPL + CLA: компании осторожно относятся к AGPL-инструментам).
5. Быстрее открываем средние репозитории (git/git, 200 тыс. файлов) — по нашим замерам на уровне или быстрее.

## 8. Топ-5 направлений, где можно отличаться (оба слабы)

1. **Хостинги «как в GitKraken», включая self-hosted и российские** — PR **и** issues, ревью-комментарии,
   статусы CI, Forgejo/Gitea/GitVerse/GitLab self-managed. У GitComet интеграций нет (Professional — GitHub и
   Azure), у AngKorGit — только PR и нет issues (в roadmap «Later»; запросы #26, #32, #47, #54). Следующие шаги:
   вход через браузер (T-068), статусы CI в графе, ревью-комментарии в diff.
2. **Workspaces / группы и stacked-ветки** — открытый запрос у обоих (GitComet #539 «virtual and stacked
   branches», AngKorGit #68 «workspace like Fork»; multi-repo workspaces — в «Later» AngKorGit). Можно сделать:
   наборы репозиториев с общими операциями и визуализацию стеков веток (rebase всего стека).
3. **Надёжность на «неудобных» репозиториях**: sparse checkout, частичные клоны, монорепо, LFS, хуки,
   worktrees — через git CLI, как в терминале. У AngKorGit хуки не работают (#82), sparse не поддержан; у
   GitComet это сильная сторона, но там нет интеграций. Нам нужно закрыть п. 2–3 из раздела 7.
4. **Локализация (минимум русский и китайский)** — нет ни у кого (GitComet #373, AngKorGit #64). Для нашей
   аудитории (GitVerse) русский интерфейс — заметное отличие.
5. **Настраиваемость и клавиатура**: настраиваемые хоткеи есть только у нас (GitComet #370, #458, #480, #651 —
   запросы на навигацию и свои сочетания). Развить: полная навигация по графу/diff с клавиатуры, схемы как в
   GitKraken/VS Code, экспорт настроек.

Отдельно стоит учесть: оба конкурента публикуют релизы каждые 1–2 недели и ведут сайты с документацией; у нас
сборки ещё не выпускались (T-069, T-004, T-056) — без этого сравнение по продукту не начнётся.
