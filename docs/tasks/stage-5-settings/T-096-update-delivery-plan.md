# T-096. Исследовать способ доставки обновлений приложения

## Цель

Выбрать понятную и проверяемую схему обновления Forklift для Linux, Windows и macOS до реализации автообновления в T-056.

## Контекст

Сейчас GitHub Actions собирает AppImage для Linux x64, установщик и ZIP для Windows x64, DMG и ZIP для macOS arm64; запуск по тегу собирает их в релиз. Подпись и нотаризация вынесены в T-004; текущие бета-сборки не подписаны. В T-056 раньше упоминался `electron-updater`, но механизм обновления, состав публикации и поведение на каждой ОС ещё не выбраны.

## Этапы

- [ ] Зафиксировать фактический путь выпуска: версия и тег, workflow, файлы релиза, ручная публикация, установка на каждой ОС. Проверить актуальность карточек T-069 и T-004.
- [ ] Сравнить для каждой ОС варианты: обновление внутри приложения, переход на страницу релиза с ручной установкой, обновление через пакетный менеджер. Указать, какие форматы пакетов и метаданные нужны каждому варианту.
- [ ] Описать безопасную доставку: проверка источника и целостности, подпись/нотариальная проверка там, где нужна, приватность запросов, права на установку, отсутствие прав администратора по возможности.
- [ ] Продумать каналы stable/beta, переход между ними, пропуск версии, откат после неудачной установки, офлайн-режим и ошибку или недоступность сервера.
- [ ] Оценить изменения в CI и релизе, стоимость сопровождения и способ проверки на реальных Windows/macOS/Linux. Подготовить короткую таблицу вариантов и рекомендацию владельцу.
- [ ] После решения владельца записать выбранную схему и критерии готовности в T-056; только затем разблокировать её реализацию.

## Критерии готовности

- Есть документ с вариантом для каждой поддерживаемой ОС, форматом публикации, ограничениями и планом проверки.
- Ясно, что пользователь увидит при наличии обновления и что произойдёт при ошибке.
- Владелец выбрал схему; T-056 обновлена по решению. Сам механизм обновления в этой задаче не реализуется.
