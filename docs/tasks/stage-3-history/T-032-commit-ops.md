# T-032. Cherry-pick, revert, reset, checkout коммита

## Цель

Операции над коммитами из контекстного меню графа: cherry-pick, revert, reset (soft/mixed/hard), checkout коммита (detached HEAD), копирование sha, создание ветки/тега на коммите.

## Контекст

- В GitKraken: CherryPick 16, Revert 8, Reset 51 (по `strings.json`); их реализация — ориентир по поведению, код свой.

## Этапы

- [x] Контекстное меню строки графа (checkout, cherry-pick, revert, reset ×3, ветка/тег здесь, копирование sha/сообщения)
- [x] cherry-pick/revert через GitCli; конфликты → T-025 (баннер); продолжить/прервать/пропустить
- [x] reset soft/mixed/hard с подтверждением (hard — предупреждение о потере изменений)
- [x] checkout коммита: предупреждение о detached HEAD; автоматический stash (как T-023)
- [x] Тесты на временных репозиториях для каждой операции и конфликтных случаев

## Критерии готовности

- Каждая операция проверена тестами и живым сценарием через контекстное меню
- Юнит/интеграционные тесты, `npm run typecheck`, `lint`, `test`, сквозной набор в `npm run test:e2e` — зелёные

## Нюансы

- 2026-10-23: cherry-pick и revert merge-коммита — относительно первого родителя (`-m 1`), как обычно и нужно
  (выбор родителя в UI — если попросят).
- 2026-10-23: остановка git с состоянием (`CHERRY_PICK_HEAD`/`REVERT_HEAD`) — это не ошибка, а «conflicts»:
  дальше баннер операции (T-025). Пустой cherry-pick (изменения уже есть) тоже оставляет состояние — баннер
  предлагает Skip. Если git отказался сразу (локальные изменения были бы перезаписаны), состояние не создаётся,
  показывается сообщение git, рабочая копия не тронута.
- 2026-10-23: cherry-pick/revert при «грязной» рабочей копии не делают автоматический stash (git сам откажет,
  если изменения мешают): решение владельца об автоматическом stash относится к переключению веток (T-023).
- 2026-10-23: пункты меню, меняющие HEAD, недоступны, пока идёт merge/rebase/cherry-pick/revert.
- 2026-10-23: проверено: юнит-тесты на реальном git и сквозной набор `commit-ops` (10 проверок).
