# T-080. История: память и отрисовка графа на сотнях дорожек

## Цель

Предложение по итогам замеров (2026-10-26, пункты 3а/3б отчёта): на linux память после чтения всей истории ≈ 1,2 ГБ (у GitComet с commit-graph 0,9 ГБ), скачки по огромной истории 100–260 мс (у GitComet — миллисекунды).

## Контекст

- `src/main/history/service.ts`: sha и родители — строки; страница раскладывается заново от состояния каждые 256 строк; SVG на строку с линией на каждую проходящую дорожку (в linux — до 590).

## Этапы

- [x] sha и родители двоично (20 байт, родители — номера строк), строки — только для отдаваемых страниц
- [ ] Отрисовка проходящих линий не по строке, а одним путём на колонку на экран (или canvas)
- [ ] Кэш раскладки последних страниц (повторные скачки рядом без пересчёта)
- [ ] Замеры: linux — память, скачки; набор в CI (T-083)

## Критерии готовности

- linux: память ≤ 0,9 ГБ после всей истории, скачки p95 ≤ 60 мс
- Юнит/интеграционные тесты, `npm run typecheck`, `lint`, `test`, сквозной набор в `npm run test:e2e` — зелёные

## Нюансы
- 2026-10-26: решение владельца: делаем; порядок владельца (2026-10-26): T-080 → T-078 → T-076 → T-077, затем T-079 и T-084.
- 2026-10-26: этап 1 — `src/main/history/commits.ts` (`CommitTable`): sha и родители байтами в растущих буферах (20 байт, в SHA-256-репозиториях 32), поиск строки по sha — открытая адресация вместо `Map`; по окончании чтения буферы ужимаются. Родители хранятся байтами, а не номерами строк: так строку не нужно искать при каждом `add`, а родитель вне истории (shallow) не требует особого случая. Формат файла истории — `FKHIST2` (сырые части таблицы; старые файлы `FKHIST1` просто перечитываются). Хэш слота — смесь первого и последнего слов sha: на последовательных sha тестов с нулями в начале зондирование вырождалось в O(n²).
- 2026-10-26: замер main на linux (1,5 млн коммитов, вся история, `process.memoryUsage`): heap 466 → 114 МБ, буферы 57 → 166 МБ, RSS 791 → 529 МБ. Основная память теперь в renderer (≈ 620 МБ после скачков) — этапы 2–3.
