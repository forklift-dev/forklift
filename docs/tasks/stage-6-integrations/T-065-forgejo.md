# T-065. Forgejo (и Gitea): вход, репозитории, pull requests, issues

## Цель

Первая интеграция этапа (приоритет владельца 2026-10-23: Forgejo → GitVerse → GitHub → GitLab): подключить
свой сервер Forgejo, видеть его репозитории для clone, pull requests и issues текущего репозитория. Заодно —
общий слой интеграций, на котором потом строятся GitVerse, GitHub и GitLab.

## Контекст

- Forgejo — самостоятельный хостинг (адрес сервера задаёт пользователь); API совместим с Gitea (`/api/v1`,
  OpenAPI на `/api/swagger`), поэтому то же подойдёт и для Gitea, и для Codeberg.
- Вход: персональный токен (Settings → Applications) или OAuth2-приложение сервера; секреты — только в
  safeStorage (как сохранённые пароли из T-024), не в settings.json.
- Пароль для HTTPS-remote уже запоминается (T-024); интеграция может выдавать git токен вместо пароля.

## Этапы

- [x] Общий слой: учётные записи хостингов (тип, адрес сервера, пользователь, токен в safeStorage), Preferences →
      Integrations, проверка токена, сопоставление remote репозитория с сервером
- [x] Forgejo API-клиент (Gitea-совместимый): пользователь, репозитории, PR, issues, комментарии; обработка
      пагинации, ошибок и самоподписанных сертификатов (только по явному согласию)
- [x] Clone: список репозиториев сервера в диалоге Clone
- [x] Панель Pull requests текущего репозитория: список, детали (описание, коммиты, файлы, комментарии), создание PR
      из ветки, checkout ветки PR
- [x] Issues: список, просмотр, создание; ссылки `#123` в сообщениях коммитов
- [x] git использует токен учётной записи для этого сервера (credential helper из T-024)
- [x] Тесты на имитации API; ручная проверка на сервере владельца

## Критерии готовности

- Сценарии проходят на Forgejo владельца
- Юнит/интеграционные тесты, `npm run typecheck`, `lint`, `test`, сквозной набор в `npm run test:e2e` — зелёные

## Нюансы

- draft до согласования; не начинать без владельца (нужен адрес сервера и тестовый токен).
- 2026-10-23: владелец дал старт («давай интеграции») и разрешил поднять Forgejo локально для проверки.
- 2026-10-23: общий слой (`src/shared/hosting.ts`, `src/main/hosting/`): учётные записи — настройка
  `integrations.accounts` (только глобально; тип, адрес, пользователь, имя — без токена), раздел Preferences →
  Integrations: «Add an account…» (сервис, адрес, токен) — токен сначала проверяется запросом `/user`, тот же
  пользователь на том же сервере заменяет токен, а не добавляет вторую запись; Remove убирает и токен. Токены —
  в `userData/hosting-tokens.json`, зашифрованы safeStorage (как сохранённые пароли T-024), без keychain добавить
  учётную запись нельзя. Токен привязан к адресу сервера, для которого его дали: настройки окно может править, и
  подмена адреса в них не отправит токен на чужой сервер. Провайдер — поле `provider` (`PROVIDERS`), клиент API —
  отдельный класс: GitVerse/GitHub/GitLab добавляются новым провайдером и клиентом.
- 2026-10-23: адрес без схемы пробуется только по HTTPS; если у сервера нет HTTPS, ошибка подсказывает ввести
  `http://` (молча на HTTP не переходим — токен ушёл бы открытым текстом). Самоподписанные сертификаты: работают
  те, что установлены в системе (запросы идут через `net.fetch` Chromium); отдельного «доверять этому серту» нет.
  Решение владельца (2026-10-23): **оставить так** (безопасность важнее).
- 2026-10-23: сопоставление remote → сервер: хост remote (https, ssh://, `git@host:owner/repo`) совпадает с хостом
  учётной записи; путь — `owner/repo` (у сервера в подпапке, `https://host/git`, подпапка снимается). Сначала
  `origin`. Результат (с веткой по умолчанию из API) кешируется, пока не изменятся remote или учётные записи.
- 2026-10-23: git и токен: credential helper приложения (T-024) сначала отдаёт сохранённый пароль, затем —
  имя и токен учётной записи для этого сервера (протокол и хост с портом совпадают, у сервера в подпапке — и путь).
  Токен не дублируется в `credentials.json`. Clone/fetch/push с сервера учётной записи идут без вопросов.
- 2026-10-23: левая панель (если учётная запись подходит к remote): секции «Pull requests» и «Issues» (открытые;
  обновить ⟳, создать +; фильтр панели ищет и по ним). Клик открывает в центре: описание (текст как есть, без
  markdown-рендера — безопасно и просто; markdown — техдолг T-067 по решению владельца 2026-10-23), ветки, mergeable, коммиты, файлы,
  обсуждение и поле комментария (Ctrl+Enter), «Open in browser», «Check out». Checkout PR: ветка этого же
  репозитория — fetch и переключение (новая следящая ветка, если локальной нет); PR из форка — fetch
  `refs/pull/N/head` в локальную ветку `pr/N` (если она уже есть — переключается на неё как есть, с уведомлением,
  не перетирая). Создать PR — из текущей ветки (её upstream на remote сервера), в ветку по умолчанию или другую;
  если ветка не запушена — предупреждение в форме. Команды палитры: Create a pull request…, Create an issue…,
  Show pull requests. `#123` в сообщении коммита и в описаниях/комментариях — ссылка на issue/PR в приложении.
- 2026-10-23: Clone: если есть учётные записи, над полем URL — список репозиториев сервера (выбор учётной записи,
  фильтр), выбор подставляет HTTPS-URL.
- 2026-10-23: «Open in browser» открывает только https-адреса (так уже устроено окно, `setWindowOpenHandler`); у
  сервера на голом http ссылка не откроется. Решение владельца (2026-10-23): **оставить так**.
- 2026-10-23: проверено: юнит-тесты на имитации (`tests/e2e/forgejoMock.mjs`: API + git по HTTP), сквозной набор
  `forgejo` (26 проверок); живая проверка на локальном Forgejo 11.0.16 в docker (`127.0.0.1:3300`, пользователи ada
  и eve, форк, PR из ветки и из форка): добавление учётной записи, clone из списка без вопросов, списки, детали PR,
  `#3` из описания, комментарий, checkout своего PR и PR из форка, push и создание PR и issue — всё прошло.
  Метки при создании issue не-участником Forgejo игнорирует сам (это не ошибка приложения). Осталась проверка на
  сервере владельца.
