# T-022. Граф коммитов и виртуализация списка

## Цель

Наглядный граф веток и слияний рядом со списком коммитов; плавная прокрутка десятков тысяч коммитов.

## Этапы

- [x] Раскладка графа (lanes) по `parents` — в main (`src/shared/graph.ts`, инкрементальная), с тестами
- [x] Отрисовка: SVG в строках списка, цвета линий — токены `--graph-0…9` (темы — T-051)
- [x] Виртуализация списка (свой, строки 28 px, в DOM только видимые ± 20)
- [x] Порционная загрузка истории вместо фиксированных 1000 коммитов
- [x] История вне реплицируемого среза `repo`: в `RepoData` только `refs` (метки) и `historyVersion`;
      строки — командой `history:rows` страницами по 200
- [x] Строка **WIP** сверху при незакоммиченных изменениях (счётчики staged/unstaged), выбор — рабочие изменения
- [x] Колонки как в GitKraken: ветка/тег │ граф │ сообщение │ автор │ дата │ sha; выбор стрелками ↑/↓

## Нюансы

- В GitKraken граф — проприетарный `@gitkraken/gitkraken-components`; пишем свой.
- 2026-10-23: обход истории — `Revwalk.commitWalk(n, { returnPlainObjects: true })` из форка nodegit GitKraken
  (C++ в потоке libuv, простые объекты). На синтетическом репозитории 100 000 коммитов: первые 500 — 0,46 с
  (топологическая сортировка всей истории), остальные 99 500 — 0,8 с; первые строки в окне — ~0,5 с.
  Порядок совпадает с `git log --all --date-order` (тест на 5000 коммитах). В `commitWalk` у подписи поле `full`
  испорчено (печатает указатель) — не использовать.
- 2026-10-23: раскладка: линия держит свою колонку, пока идёт (линии прямые), освободившаяся колонка переиспользуется.
  Коммит встаёт в самую левую из ждущих его линий, остальные заканчиваются в нём (точка ответвления). Первый
  родитель продолжает линию коммита, кроме случая, когда родителя уже ждёт линия **левее** — тогда коммит
  «вливается» в неё; линия правее не перехватывается (она уже нарисована выше), обе сходятся у родителя — как в
  `git log --graph`. Инвариант (тест, в том числе на случайных историях и на 5000 коммитах): набор линий сверху
  каждой строки равен набору снизу предыдущей.
- 2026-10-23: история в main кэшируется на вкладку и версию (`historyVersion` = хэш HEAD + всех веток/удалённых
  веток/тегов); новая версия → обход заново. Окно держит страницы прошлой версии, пока не придут новые, — после
  коммита список не мигает. Кэш вкладки удаляется при её закрытии.
- 2026-10-23: история подгружается по мере прокрутки: высота списка = пройдено + 1 страница, пока история не
  кончилась, поэтому ползунок уточняется по мере прокрутки. Фоновый обход всей истории не делается (на очень
  больших репозиториях это память и время) — можно добавить с ограничением, если понадобится.
- 2026-10-23: строка WIP ставит узел в колонку HEAD и рисует пунктир вниз, только если HEAD — первая строка
  истории; иначе узел WIP в колонке 0 без линии (так бывает, когда новее HEAD есть коммиты в других ветках).
- 2026-10-23: `scripts/make-history-repo.mjs <dir> [коммитов] [seed]` — генератор ветвистой истории через
  `git fast-import` для тестов и замеров (используется в юнит- и сквозных тестах).
- 2026-10-23: проверено: юнит-тесты раскладки и HistoryService, сквозной набор `graph` (13 проверок, включая
  прокрутку 3000 коммитов до первого), все остальные наборы зелёные.
- 2026-10-26: переделано по итогам замеров на linux (1,5 млн коммитов; `docs/research/competitors-2026-10.md`):
  было — revwalk libgit2 с полной топологической сортировкой до первой строки (10–20 с), каждая строка с полным
  списком рёбер в памяти main (в linux до 590 дорожек, ~250 рёбер на строку) — 5–8 ГБ и падение при прокрутке к
  концу. Стало (`src/main/history/service.ts`):
  - история читается потоком `git log --date-order` (с commit-graph первые строки ~1–2 с даже на linux; без него
    git сам сортирует ~11 с); процесс-хост умеет отдавать вывод потоком, не копя его (`streamOnly`);
  - данные коммитов — по столбцам (sha, родители строкой, автор — общий индекс, время, тема), без объекта на строку;
  - граф не хранится: каждые 256 строк сохраняется состояние раскладки, страница раскладывается заново от
    ближайшего; при чтении состояние двигает `GraphLayout.advance` — то же, что `next`, но без рёбер и с индексом
    дорожек (вся история linux — ~3 с вместо 37); тесты — совпадение `advance` и `next`, страницы из середины и
    сплошной раскладки;
  - окно держит не больше 64 страниц истории (дальние от места прокрутки выбрасывает и запросит снова);
  - Chromium ограничивает высоту элемента ~33,5 млн px (≈ 1,1 млн строк по 30 px): дальше строк не было видно.
    Высота прокрутки ограничена 30 млн px, позиция прокрутки переводится в «виртуальную» пропорционально (на
    истории linux колесо крутит в ~1,5 раза быстрее; до ~1 млн строк масштаб 1 и ничего не меняется).
  Итог на linux (упакованная сборка, commit-graph есть): первые строки 1,4 с (было 10–20 с), вся история до самого
  старого коммита — 17 с (было: падение), память 1,9 ГБ после загрузки всей истории (было 5–8 ГБ).
- 2026-10-26: структура и подробности истории читаются раздельно (как у GitComet, идея из их docs): форма — поток
  `git rev-list --date-order --parents` (на linux с commit-graph — 2,3 с на всю историю), автор, дата и тема —
  `git log --no-walk=unsorted --stdin` блоками по 256 строк только для показанных страниц (~10 мс на блок), до 256
  блоков в памяти. Палитре коммитов (Ctrl+P) темы всех коммитов читаются отдельно, при первом поиске. Итог на linux:
  вся история до самого старого коммита — ~4,3 с от открытия (было 17 с), память 1,2 ГБ (было 1,9 ГБ).
- 2026-10-26: worker-поток для разбора истории не нужен: пока читается вся история linux, лёгкая IPC-команда
  отвечает с медианой 0 мс и p95 19 мс (разбор идёт кусками по чанкам вывода; был один всплеск 0,4 с, похоже, GC).
- 2026-10-26: история сохраняется между запусками (`src/main/history/store.ts`, `userData/history`): после полного
  чтения истории от 20 000 строк — форма в двоичном виде (sha по 20 байт, родители и дорожки контрольных точек —
  номерами строк, stash-строки) с ключом «версия истории + фильтр»; при той же версии повторное открытие берёт
  историю с диска без `git rev-list` (подробности — как обычно, по блокам). Хранятся последние 8 репозиториев.
  linux: без commit-graph — первые строки 10,1 → 1,8 с, самый старый коммит 13,7 → 2,4 с; с commit-graph —
  1,4 → 1,1 с и 5,2 → 1,2 с; файл 51 МБ. Новые коммиты не дописываются (в `--date-order` они могут встать в
  середину, а раскладка ниже всё равно меняется): другая версия читается заново и сохраняется снова.
